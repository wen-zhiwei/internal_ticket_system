用 Codex 做一个客服协作工作台

从一句自然语言需求，到一套能创建、分配、协作、查询和验证的真实系统。这里记录的不是“AI 生成了几行代码”，而是人如何和 Codex 一起拆需求、做决策、改代码、跑验证。

项目：客服协作工作台 场景：滴滴自动驾驶客服 开发方式：对话驱动 + Feature 切片 当前记录：2026-09-21
01 / 起点

先把复杂目标说清楚

项目不是从“做一个页面”开始，而是从客服每天要处理什么、哪些动作需要协作、哪些操作必须确认开始。

要解决的问题

让客服在一个工作台里看到工单、处理工单、和同事协作；再用“我的助手”降低查询和录入成本，但不让 AI 越权替人做关键决定。

产品边界

演示身份来自数据库；核心业务走 Go API 和 PostgreSQL；前端不拿静态 Mock 冒充真实业务；AI 只通过结构化工具进入后端服务。

02 / 方法

需求是这样落地的

每一轮都保持同一个节奏：先确认边界，再切一个能验收的功能，最后用命令和真实接口证明它确实工作。

STEP 01

自然语言描述

例如：“历史会话放在左侧可收缩菜单，点进去继续和我的助手对话。”

STEP 02

Codex 拆成 Feature

明确页面、接口、数据表、权限、验收条件，避免直接做一大团“完整业务”。

STEP 03

修改真实代码

前端、Go API、迁移和测试一起改；核心数据不使用静态 Mock。

STEP 04

跑验证再交付

格式、Lint、测试、构建、差异检查和真实 API 请求逐项确认。

关键决策 A

不单独训练意图识别模型

让大模型读取当前允许使用的工具说明，自行选择结构化工具；后端仍然负责权限和业务校验。

关键决策 B

AI 不直接执行 CLI 或数据库

前端、AI Tool 和未来 CLI 都复用同一个 TicketService，避免多套业务逻辑互相漂移。

关键决策 C

写操作先确认，查询可以直接展示

整理草稿不等于创建工单；批量修改先列出对象，用户确认后才执行。

关键决策 D

先做最小记忆，不保存敏感内容

第一版只记默认日期范围、时区、常用视图和回复偏好；会话上下文用 conversation_id 管理。

03 / 结构

AI 是入口，不是权限中心

“我的助手”负责理解自然语言和组织结果；真正能不能查、能不能改，由 Go 后端的业务服务决定。

用户自然语言
      ↓
Go Assistant API  ── 每次请求传入当前可用的工具说明
      ↓
模型选择结构化工具  ── 不给模型数据库权限，不执行任意 Shell
      ↓
ToolRegistry / TicketService
      ↓
权限校验 · 状态校验 · 参数校验 · 事务 · 幂等
      ↓
PostgreSQL
      ↓
结构化结果 / 前端卡片  ── 列表卡片、详情卡片、草稿卡片、确认卡片

失败也走结构化结果：ok、code、retryable、message。临时故障最多有限重试，权限、参数和状态冲突不盲目重试。

工具它做什么为什么安全
search_tickets按时间、状态、负责人等条件查询工单只返回当前用户有权限看到的结果
get_ticket_detail查看一张工单的详情、协作和操作历史后端再次校验工单可见范围
prepare_create_ticket把自然语言整理成可编辑的工单草稿只准备，不真正写入；确认后仍调用正式创建 API
04 / 过程

从基础能力到协作工作台

下面是本次开发的主要 Feature 轨迹。每个切片都有代码变化和验证结果，而不是只停留在方案图上。

FEATURE 01–05 · 基础骨架

身份、工单、SLA 与状态动作

建立演示用户与角色；完成工单创建、列表、详情、筛选、分页、SLA、领取、分配、改派、状态机、评论、历史和编辑。

FEATURE 06–09 · 首页和效率

问候、快捷视图、记忆、统计和侧栏

加入按时间问候、保存查询标签、轻量用户偏好、今日工作概览、pending/overdue 筛选和可收缩左侧目录。

FEATURE 10–12 · 工作台重构

双岛首页与“我的助手”

左侧是对话入口，右侧聚焦工单；统一品牌文案；移除重复入口；助手支持查询卡片、草稿整理和确认创建。

FEATURE 13–15 · 会话连续性

历史会话成为独立二级菜单

历史会话按用户保存到 PostgreSQL；点进记录后打开对应对话；继续发送时携带原 conversation_id。

FEATURE 16–18 · 协作和可用性

详情页协作增强与无横向滚动

评论放到右侧；改派支持搜索姓名和团队；顶部突出处理人、团队、客户和 SLA；工单列表在窄屏改为信息卡，避免左右滑动。

06 / 对话

AI 对话不是聊天，是共同做设计

下面摘录几轮真正影响架构和产品的讨论。用户提出问题，Codex 解释取舍，再把结论落实到代码和验证。

用户提问
“AI 整理工单草稿为什么不设计成一个意图 intent？”
结论：第一版不单独训练意图模型，让大模型根据工具说明选择结构化工具；减少一层分类维护。
用户追问
“每次请求都要把完整工具列表给模型吗？”
结论：后端按当前场景传入允许工具及说明，模型选择工具；Go 代码负责执行和校验，不把判断权交给前端。
用户质疑
“工具执行失败怎么办？第二次模型调用怎么保障？”
结论：工具结果先结构化表达 ok、code、retryable、message；临时故障有限重试，业务冲突不重试，并让前端直接显示可理解的错误卡片。
界面反馈
“左右滑动太不方便，工单中心要尽量避免横向滚动。”
结论：压缩列宽和间距，窄屏切换为纵向信息卡；视觉调整也必须经过真实页面验证。
07 / 结果

最终交付的不只是一个助手

AI 被放在客服真正的工作流里：查得到、理得清、改之前能确认，改完以后回到真实工单中心。

原始需求语言

  • 帮我查一下今天要处理哪些。
  • 帮我创建一个订单重复扣费工单。
  • 历史会话放左侧，可以展开收起。
  • 评论放右侧，改派要能搜索团队。
  • 不要左右滑动，首屏多展示工单。

已落地 系统能力

  • 助手返回真实工单列表卡片，点击进入详情。
  • 自然语言整理草稿，补齐必填项，确认后创建。
  • 独立历史会话页，继续发送保留会话上下文。
  • 详情页右侧评论、团队/人员搜索、协作信息置顶。
  • 列表响应式适配，窄屏改为纵向信息卡。

适合演示的一句话

我不是让 AI 直接写一个 Demo，而是用 Codex 把自然语言需求拆成可验收的 Feature，让前端、后端、数据库、权限和测试一起形成闭环。

08 / 底线

高标准来自这些小规则

AI 可以帮忙理解和编排，但系统的安全边界、业务规则和可验证性不能交给模型猜。

工程规则

  • 状态机、权限、并发领取、输入校验由后端强制校验。
  • 数据变更和操作历史在同一个数据库事务内完成。
  • 业务冲突优先返回 409；不存在 404；参数错误 400；无权限 403。
  • SQL 使用参数化查询，不拼接用户输入。

展示页的安全处理

  • 本页只展示脱敏后的开发过程摘要。
  • API Key、数据库密码、Token 和绝对路径不进入页面。
  • 模型服务配置仅保存在本机后端环境变量。
  • 这不是原始会话导出，而是可对外分享的开发复盘。
